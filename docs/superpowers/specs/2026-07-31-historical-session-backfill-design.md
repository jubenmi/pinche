# 历史车局补录与未来拼车时间选择设计

日期：2026-07-31

## 结论

车局创建流程同时支持两种用途：

- `future_carpool`：开本时间在未来，用于同城发现、分享招募、申请审核和上车。
- `historical_record`：开本时间已经过去，用于补录已玩车局、认领当时角色、上传相册和填写复盘。

采用显式持久化的车局用途，不只依赖 `start_at <= now` 推断。历史补录不进入同城发现，不接受普通报名或 NPC 自选；只能通过专用补认邀请加入当时的同车成员。

## 背景与根因

创建页把日期选择器的最早日期设为今天，无法选择过去日期。时间选择器则没有传入明确的 `start` 和 `end`。当前 TDesign 纯时间模式会将缺省最小日期的时分带入选项边界，导致无论选了哪个未来日期，都只能选择当前时间之后的时分。

后端创建接口目前不校验时间是否在未来，但现有创建流程会继续调用发布接口，将所有车局无条件设为 `recruiting`。过去车局虽会被同城发现的未来时间条件过滤，但分享链路和报名 API 仍可以让用户上车，并且管理页会显示“招募中”。因此，只放开过去日期会造成业务语义和权限漏洞。

## 方案选择

### 采用：显式车局用途

为车局增加明确的 `session_purpose`，取值限定为 `future_carpool` 和 `historical_record`。它回答“这条记录为什么被创建”，而 `start_at` 继续回答“什么时候开本”。

这个方案可以保留普通车局开始后的现有相册生命周期，同时对补录车局进行稳定的文案和权限判断。

### 不采用：仅从时间推导用途

仅使用 `start_at <= now` 会让一辆普通未来拼车在到点后被重新解释为“补录”，也无法对补录邀请和普通招募邀请做安全隔离。

### 不采用：建立独立历史记录实体

单独的历史表语义清晰，但会重复角色、成员、相册、照片权限和复盘等现有能力，超出本次需求。

## 时间选择与模式判定

1. 日期选择器允许选择过去和未来日期，不再以今天作为最早日期。
2. 纯时间选择器显式传入同一个锚点日期的 `00:00` 和 `23:59` 边界，保证任意日期都能选择全天时间。
3. 页面将日期和时间合成一个上海时区的开本时间，比较当前时刻：
   - 严格晚于当前时刻：`future_carpool`。
   - 早于或等于当前时刻：`historical_record`。
4. 日期或时间变更后立即重新计算用途，不需要用户手动切换。
5. 提交时再次以当前时刻计算。如果原本的未来时间已经过去，不静默转换；页面改为历史补录提示并要求用户再次点击创建。

## 创建页交互

### 未来拼车

- 保留“上车权限”、同城展示、置顶集合信息和“创建车局并分享”。
- 未来日期可以选择任意当天时间，例如 8 月 3 日 13:00，不再受 7 月 31 日当前小时限制。

### 历史补录

- 在时间区块下方显示高优先级提示：“当前为历史补录，仅用于记录已完成的车局，不会发布未来拼车。”
- 隐藏上车审核、必须留电话、NPC 自选和同城展示等招募设置。
- 不使用“集合”式默认置顶文案。历史记录可保留一个可选的“补录说明”，留空时不自动生成未来集合信息。
- 底部按钮改为“创建历史补录”。

## 数据模型和生命周期

### `session_purpose`

在 `sessions` 中新增非空字段，默认值为 `future_carpool`，以保持现有数据和老客户端兼容。后端对取值做白名单规范化，不接受任意字符串。

创建时服务端校验用途和时间一致：

- `future_carpool` 必须严格晚于服务端当前时刻。
- `historical_record` 必须早于或等于服务端当前时刻。
- 时间必须使用现有业务时区规则可确定地解析；无效时间返回 400。

### 内部状态

普通车局继续使用现有 `draft -> recruiting` 流程。

历史补录在完成座位初始化和创建者角色绑定后落为 `locked`，用户层不显示“已锁车”，而是优先根据 `session_purpose` 显示“历史补录”。不新增与 `status` 并行的 `completed` 状态。

补录车局即使为 `locked` 也不得走现有“已开始且已锁车的空位仍可上车”例外；是否可加入必须先检查 `session_purpose`。

## 创建和补认数据流

### 创建者

1. 客户端提交时间、`sessionPurpose`、店家、剧本和已选角色。
2. 后端校验用途和时间边界，创建 `draft` 车局并复制角色。
3. 现有创建编排继续初始化座位。
4. 客户端从初始化结果中找到创建者选中的座位 ID。普通车局仍以空请求发布为 `recruiting`；历史补录向同一发布接口传入 `creatorSeatId`。
5. 历史发布分支在单个后端事务中验证该座位属于本车局，绑定创建者，建立已通过的成员记录和复盘资格，再将车局设为 `locked`。如果座位无效或不属于该车局，整个发布事务失败。
6. 历史发布必须在后端受控逻辑中完成，不允许客户端通过通用 `PATCH` 任意修改用途或状态。

### 同车成员补认

1. 车头从历史车局中调用 `POST /api/sessions/:id/historical-invite-token` 生成专用的补认邀请。
2. 邀请令牌必须绑定车局、补录用途和有效期，不能当作普通招募令牌使用。
3. 受邀用户看到“补认当时角色”而非“申请上车”。
4. 用户选择一个尚未被占用的玩家角色或 NPC 角色后，客户端调用专用的 `POST /api/sessions/:id/historical-claims`，传入 `inviteToken` 以及二选一的 `seatId` / `npcRoleId`。服务端验证专用令牌并直接建立已通过的成员关系，不进入待审队列。
5. 补认成功后，用户获得同车成员的相册和复盘权限，并设置可复盘资格时间。
6. 没有专用邀请令牌时，普通报名、直接占位和 NPC 自选 API 必须拒绝历史补录。

## 发现、分享和页面展示

- 同城发现和公开 upcoming 列表在现有未来时间过滤之外，明确加入 `session_purpose = 'future_carpool'`。
- 历史补录强制使用 `share_only` 可见性，即使老客户端传入 `public` 也由服务端收紧。
- 普通车局分享仍为“邀请好友认领角色”。
- 历史补录分享为“邀请当时同车玩家补认角色”，不展示招募、审核或缴费语义。
- “我的日程”继续按 `start_at` 展示记录。历史补录卡片标记“历史补录”，主行动为打开相册。
- 详情、管理、分享和相册页必须优先根据 `session_purpose` 选择文案和操作，不能让底层 `locked` 状态泄露成“已锁车”或“招募中”。

## 相册与复盘

历史补录的 `start_at` 已在过去，因此复用现有“已发车”相册开放规则。车头在历史补录创建完成后立即获得：

- 上传照片和视频的权限。
- 查看同车成员相册的权限。
- 创建或编辑复盘的资格。

通过专用补认邀请加入的成员获得相同的同车成员内容权限。照片可见性、作者私有内容和审核边界不做改变。

## 通用更新边界

现有车局通用 `PATCH` 不得任意修改 `session_purpose`。本次同时收紧 `status` 更新，只接受业务层已有的合法取值和转换，防止老客户端或手工请求绕过补录生命周期。

## 错误与边界

- 客户端和服务端对时间用途的判定不一致时，服务端返回可识别错误码；客户端刷新提示并要求用户再次确认。
- 历史补录请求传入公开可见性或招募设置时，服务端收紧为补录安全默认值，不信任客户端。
- 无效、过期、车局不匹配或用途不匹配的补认令牌返回 403，且不暴露车局内容。
- 同一用户不能重复补认多个玩家角色；角色并发补认时使用事务和行锁保证只有一人成功。
- 已取消车局不允许新的补认。
- 补录记录已创建但座位初始化失败时，保持 `draft` 并给出可重试错误，不暴露一个部分可用的补录给其他用户。

## 测试与验收

1. 在 7 月 31 日 17:00 打开时间选择器，选择 8 月 3 日后，可以选择 13:00。
2. 今天和过去日期的时间选择器都可以选择 00:00–23:59，并由合成时间自动选择用途。
3. 选择过去时间时显示历史补录提示，隐藏招募设置，且创建按钮使用补录文案。
4. 未来拼车只能以未来时间创建，历史补录只能以过去时间创建。
5. 历史补录强制为 `share_only`，不出现在同城发现或公开 upcoming 列表。
6. 历史补录不能通过普通报名、直接占位或 NPC 自选 API 加入。
7. 有效的专用补认邀请可以让受邀用户直接认领一个未占用角色，并获得相册和复盘资格。
8. 过期或用途不匹配的令牌不能补认，并发只有一人可以获得同一角色。
9. 历史补录在日历、详情、管理和分享页都显示补录语义，不显示“招募中”或“已锁车”。
10. 创建者和补认成员可立即访问历史车局相册、上传内容并填写复盘。
11. 现有未来拼车的创建、分享、申请、审核、同城发现和发车后相册行为保持不变。
12. 老数据和未传 `sessionPurpose` 的兼容客户端按 `future_carpool` 处理，不会被批量改为补录。

## 非目标

- 不建立独立的历史记录表或第二套相册系统。
- 不将补录相册变成公开内容广场。
- 不自动把所有已过开本时间的普通车局转换为历史补录。
- 不改变现有照片隐私、内容审核和作者私有规则。
- 不在本次需求中支持车头随意将普通车局和历史补录相互转换。

## 自检

- 无 `TBD` 或待决策项。
- `session_purpose` 和 `start_at` 的职责分开，不会随时间流逝改变车局创建用途。
- 补录车局的发现、招募、邀请、成员、相册和复盘权限一致。
- 普通未来拼车和现有已发车相册生命周期不受影响。
- 强制性安全规则落在服务端，不依赖隐藏前端按钮。
- 改动集中在现有车局创建、分享和成员边界，不重建平行系统。
