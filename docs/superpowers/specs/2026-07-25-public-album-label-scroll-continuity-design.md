# 公开相册标签与分页滚动连续性设计

日期：2026-07-25

## 结论

公开相册卡片应展示与成员相册一致的标签文字，但公开接口只返回脱敏后的标签文字数组，不返回原始标签对象、用户 ID、席位 ID 或标签关联关系。

公开相册触底分页应把新媒体增量加入现有瀑布流，不能清空第一页后重建。初次载入、切换成员相册筛选等真正需要替换整个列表的场景仍可使用完整刷新。

实现和验证以最新 `develop` 为基线，在独立 `codex/` 分支与 worktree 中进行。当前工作区的 `codex/album-share-icon-state` 分支早于线上分页实现，且存在与本任务无关的未提交文件，本任务不得修改或提交这些文件。

## 背景与根因

### 分享页标签全部显示“其他”

成员相册接口返回完整的 `photo.tags`，卡片通过 `tagSummary()` 显示：

```text
照片里：沈清商、阿离
```

公开分享接口虽然在服务端已经读取并校验了同一组标签，但公开 DTO 会把 `tags` 固定为空数组，只额外返回二元分类：

- 包含分享者席位：`public_category = "share_subject"`
- 其他所有情况：`public_category = "other"`

公开页只能把第一类显示为“包含分享者角色”，NPC、其他角色、场景标签和缺少分类的数据都会显示成“其他”。因此问题来自 DTO 信息被过度压缩，不是前端样式或照片数据缺失。

### 触底加载后跳回顶部

公开页的 `onReachBottom()` 会请求下一页并正确合并媒体，但成功后复用了 `refreshWaterfall()`。该方法会：

1. 清空两列已渲染数据；
2. 调用瀑布流组件的 `clear()`；
3. 把绑定数组设置为空；
4. 在后续 tick 中重新插入全部媒体。

公开页使用微信原生页面滚动。瀑布流被清空时文档高度瞬间收缩，微信会把当前滚动位置钳制到新的有效范围；内容重新插入后不会自动恢复原位置。

`uv-waterfall` 已支持增量模型更新：绑定数组变长时，它只处理新数组相对旧数组增加的尾部项目。因此分页无需完整重建。

## 方案比较

### 方案 A：脱敏标签投影 + 瀑布流增量追加（采用）

服务端返回 `public_tag_labels`，只包含已经通过当前分享资格、审核和隐私复核的媒体标签文字。公开页复用成员相册的摘要格式。分页只把去重后的新增媒体追加到瀑布流模型。

优点：

- 满足“分享页标签与相册一致”；
- 不公开标签 ID、用户 ID、席位 ID、账号昵称映射等内部数据；
- 保留现有卡片 DOM 和滚动锚点；
- 改动集中，能用纯函数和页面契约测试覆盖。

### 方案 B：公开完整 `tags`

前端可直接复用 `tagSummary()`，机械改动较少，但会公开标签主键、用户和席位关联等成员域数据，违反既有公开 DTO 最小化边界，不采用。

### 方案 C：保留通用文案并在重建后恢复滚动距离

前端仍无法得到真实标签，不能满足标签需求。手动记录并恢复滚动距离还会受到图片异步高度、瀑布流分列和渲染时序影响，容易闪动或定位偏差，不采用。

## 数据与接口设计

公开媒体 DTO 新增：

```json
{
  "tags": [],
  "public_tag_labels": ["沈清商", "阿离"]
}
```

规则如下：

1. `public_tag_labels` 只由服务端当前已经读取的合规标签生成，不接受客户端输入。
2. 每个元素必须是去除首尾空白后的非空字符串。
3. 按成员相册标签既有顺序输出，并对相同文字去重。
4. 不返回标签类型、标签 ID、`user_id`、`seat_id`、`session_npc_role_id`、`seat_user_id` 或账号映射。
5. 原有 `tags: []` 保持不变，避免其他公开消费者误把展示文字当作授权数据。
6. 审核、快照、上传者公开开关、被标注者公开开关、删除、撤销和分享过期规则保持不变。
7. 资格复核不通过的媒体仍整体不返回；不能只隐藏标签后继续公开媒体。

这一设计有意修订 D48 “公开页不返回原始标签”的展示结论，并局部取代 D54 Requirement 5.3 对“标签名材料”的禁止：原始标签对象仍不返回，但经脱敏的角色/场景标签文字可以随已经获准公开的媒体返回。标签文字仅用于展示，不参与客户端权限判断；D48/D54 对上传者身份、账号资料、标签关联字段和内部快照资格的禁止保持不变。

## 小程序展示设计

公开页卡片使用 `public_tag_labels` 生成与成员相册一致的摘要：

- 图片有标签：`照片里：沈清商、阿离`
- 视频有标签：`视频里：沈清商、阿离`
- 本人上传并通过分享快照显式纳入的未标注图片：`待标注`

前端必须把缺失、非数组、空白或非字符串标签当作无标签处理，不能回退到旧的 `public_category = "other"` 并再次显示错误的“其他”。

`public_category` 可在兼容期继续存在，但新页面展示不再依赖它。旧客户端继续使用旧文案，不影响分享访问能力。

## 分页与瀑布流设计

首次公开相册载入继续完整初始化瀑布流。后续页成功返回时：

1. 使用现有分页合并规则按媒体 ID 去重；
2. 得到本次真正新增的媒体集合；
3. 更新完整的 `photos` 数据；
4. 只把新增媒体追加到 `waterfallPhotos`；
5. 保留 `waterfallList1`、`waterfallList2` 和已经渲染的卡片；
6. 由 `uv-waterfall` 把新增媒体分配到当前较短的列；
7. 在新增卡片完成分列后更新可见性观察；观察器更新不得清空或重建已有卡片 DOM。

加载更多路径不得调用：

- `refreshWaterfall()`；
- 瀑布流组件 `clear()`；
- `waterfallPhotos = []`；
- `uni.pageScrollTo()` 进行事后补偿。

完整刷新仍只用于首次载入、成员相册筛选改变或明确替换整个列表的场景。公开模式下的签名 URL 后台刷新必须重新读取当前已经加载的公开前缀，不能只取第一页；媒体 ID 序列未变化时，应原位更新媒体字段和现有瀑布流行，不得重建卡片。只有审核、删除或隐私复核确实改变了媒体 ID 序列时，才允许按新的授权结果替换整个列表。

## 竞态与错误处理

- 重复触底请求继续由 `publicShareLoadingMore` 和列表请求 authority 阻止。
- 迟到的旧分页响应不得写入当前相册。
- 下一页存在重复媒体 ID 时只保留已有卡片，不重复追加。
- 下一页请求失败时保留已经展示的所有媒体、列分配和滚动位置，并继续显示现有重试入口。
- 下一页没有新增媒体但仍有合法游标时，只更新游标状态，不重建列表。
- 分享过期、撤销或访问凭证失效继续走现有不可访问流程。
- 媒体在分页期间被删除或隐私收紧时，以服务端当前复核结果为准，不由客户端补回。

## 测试设计

### 服务端

1. 公开媒体拥有多个标签时，DTO 返回按顺序去重的 `public_tag_labels`。
2. DTO 的 `tags` 仍为空数组。
3. 序列化结果不包含标签 ID、用户 ID、席位 ID、NPC 角色 ID 或账号映射。
4. 未标注快照媒体返回空 `public_tag_labels`。
5. 既有隐私否决、删除、撤销、审核和 token 测试保持通过。

### 小程序纯函数

1. 图片标签生成 `照片里：标签A、标签B`。
2. 视频标签生成 `视频里：标签A、标签B`。
3. 空标签生成 `待标注`。
4. 非法、空白和重复标签被安全归一化。
5. 分页合并同时返回完整列表和本次新增的唯一媒体。

### 页面集成契约

1. `loadMorePublicAlbum()` 成功路径只调用增量追加方法。
2. 该路径不包含 `refreshWaterfall()`、`clear()` 或清空瀑布流模型的操作。
3. 首屏媒体 ID 在分页前后保持挂载，只有新 ID 被追加。
4. 分页失败不修改已有媒体和瀑布流列。
5. 公开模式后台 URL 刷新覆盖已加载前缀；ID 序列不变时不重建瀑布流，ID 序列因授权复核变化时才完整替换。

### 验证

运行相关 API 单测、小程序标签与分页单测、D48/D50/D54 回归门禁、小程序构建以及 `git diff --check`。在微信开发者工具中用超过 30 项的公开相册完成一次实机检查：滚动到第一页底部触发分页，确认新卡片在原位置下方出现且页面不回到顶部。

## 范围外

- 不改变哪些媒体有资格进入公开分享。
- 不公开上传者昵称、账号资料或标签关联 ID。
- 不修改相册标签内容或自动写入“其他”。
- 不重做瀑布流布局算法。
- 不使用手动滚动补偿掩盖列表重建。
