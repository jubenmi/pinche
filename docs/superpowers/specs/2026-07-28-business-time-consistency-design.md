# 业务时间一致性设计

**日期：** 2026-07-28

**状态：** 已确认，等待书面规格复核

**基线：** `origin/develop@0918768a`
**目标：** 消除车局业务时间在创建、传输、存储、展示和日期边界上的时区歧义，同时保证已经正确的 UTC 数据与行为不变。

## 1. 背景与根因

车局创建页把用户选择的北京时间拼成无时区字符串，例如 `2026-07-28 15:00:00`。API 未归一化该值，直接把字符串绑定到使用 UTC 会话的 MySQL `DATETIME`。数据库保存数字 `15:00:00`，mysql2 读回时把它解释为 `15:00Z`，北京时间展示函数随后显示为 `23:00`。

正确链路应为：

```text
北京时间选择 2026-07-28 15:00
  -> ISO/UTC 2026-07-28T07:00:00.000Z
  -> UTC DATETIME 2026-07-28 07:00:00
  -> API ISO 2026-07-28T07:00:00.000Z
  -> 北京时间展示 2026-07-28 15:00
```

2026-07-17 的既有修复已经正确统一了共享格式化工具、主要页面展示和 MySQL UTC 会话，但没有覆盖初次创建入口。现有测试分别验证转换、展示和数据库配置，没有串联“选择 -> 请求 -> 数据库 -> API -> 页面”的完整闭环，因此形成假绿。

## 2. 安全约束

本设计把“已经正确的不要改”作为硬性验收条件：

- 不修改数据库表结构、字段类型、MySQL `timezone: "Z"` 或 `SET time_zone = '+00:00'`。
- 不新增数据迁移，不对生产库执行 `UPDATE`、`DELETE` 或自动修正。
- 不修改已经正确的改期、历史纠时、`CURRENT_TIMESTAMP` 生命周期比较、有效期、租约和清理逻辑。
- 不为了统一风格而改动行为已经正确且不在本次数据流中的代码。
- 对必须接入共享能力的兼容路径，先增加正确行为的特征测试，保证显式 ISO/UTC 输入改前改后输出完全一致。
- 无法证明语义的历史记录一律归类为“无法判定”，不修改。

截图对应的车局 161 当前只读 API 值为 `2026-07-28T07:00:00.000Z`，对应北京时间 15:00，属于正确样本，不进入任何修正范围。

## 3. 方案选择

### 3.1 采用方案：共享业务时间内核 + 各端薄适配

`@pinche/shared` 继续作为唯一业务时间语义来源。小程序、管理端、API 和 `talk` 插件只负责各自输入输出适配，不再自行加减八小时、截取 ISO 字符串或依赖设备本地时区。

该方案同时覆盖客户端、服务端和插件边界，能够阻止旧客户端继续写错，又不需要修改数据库。

### 3.2 未采用方案

- **只修创建页面：** API、旧客户端、后台入口、通知和日期边界仍可能产生或展示错误。
- **修改数据库时区或字段类型：** 迁移风险大，且无法区分混合语义的历史 `DATETIME` 数据。
- **批量减八小时：** 会破坏已经由改期、历史纠时或其他正确 UTC 路径写入的数据，禁止采用。

## 4. 统一时间组件职责

现有以下正确函数继续保留：

- `parseBusinessDateTime`
- `formatBeijingDateTime`
- `beijingDateKey`
- `beijingTimeText`
- `beijingWallTimeToIso`

在同一模块中补充小而明确的纯函数：

### 4.1 `businessDateTimeToPickerValue(value)`

把显式 ISO、`Date` 或历史无时区值转换为 `{ date: 'YYYY-MM-DD', time: 'HH:mm' }`。显式 ISO 按绝对时间转换为北京时间；无时区值按历史兼容规则视为北京墙钟时间；非法输入返回 `null`。

### 4.2 `formatBeijingShortDateTime(value, fallback)`

输出聊天等紧凑场景需要的 `MM-DD HH:mm`，语义与 `formatBeijingDateTime` 完全一致。

### 4.3 `isBusinessDateTimeReached(value, now)`

通过 `parseBusinessDateTime` 比较 epoch，统一兼容显式 ISO 和历史北京墙钟值。无效输入安全返回 `false`。

### 4.4 `beijingDayUtcRange(dateKey)`

把北京日期 `YYYY-MM-DD` 转换为 UTC 半开区间 `[start, end)`。例如北京时间 2026-07-29 对应 `2026-07-28T16:00:00.000Z` 至 `2026-07-29T16:00:00.000Z`。非法日期返回 `null`。

这些函数必须是纯函数，不读取浏览器、Node 或设备的本地时区。

## 5. 写入数据流

### 5.1 小程序与管理端创建入口

两个创建入口都保留 picker 中的北京墙钟值作为表单状态，在发送请求前调用 `beijingWallTimeToIso`：

- 小程序 `pages/session/setup.vue`
- 管理端 `MiniProgramWorkspace.vue`

转换失败时阻止请求并使用现有的创建失败提示。草稿仍保存用户选择的北京墙钟语义；从 API ISO 或旧草稿恢复时使用 `businessDateTimeToPickerValue`，禁止直接切字符串。

小程序创建页的“今天”“明天”和最小可选日期改为基于北京时间日期键计算，不能依赖设备本地 getter。管理端现有北京时间默认日期逻辑已经正确，保持不动。

### 5.2 API 创建边界

API 在 `createSessionWithConnection` 写数据库前集中归一化 `startAt`：

- 显式 `Z` 或 offset ISO：保留其绝对时间语义，归一到 MySQL 秒精度后绑定 `Date`。
- 旧客户端无时区值：明确按北京时间墙钟解释，再转换为 `Date`，兼容旧版本但不再产生八小时偏差。
- 缺失或非法日历值：返回 400，事务中不产生任何业务写入。

归一化后的值必须以 `Date` 绑定到 mysql2，不能把原始字符串直接传给 `sessions.start_at`。API 响应继续由 JSON 序列化为显式 UTC ISO。

改期和历史纠时已有更严格的显式时区合同与审计语义，不复用创建兼容策略，也不修改其实现。

## 6. 确认错误的展示与通知点位

以下点位存在可重复证明的 UTC、设备本地时区或字符串截取错误，改为调用共享能力：

- 小程序相册上传时间。
- 小程序资料审核提交时间。
- 小程序伪聊天消息时间。
- 小程序待审核报名提示时间。
- `talk` 子模块聊天时间与默认置顶文案。
- 报名创建、报名审核订阅消息的车局时间。

`talk` 声明 `@pinche/shared` 为宿主提供的 peer dependency，并直接导入纯时间 helper，不复制固定 `+8` 逻辑；主工程 workspace 负责提供该 peer。主工程更新固定的子模块提交，并同步处理主工程中因平台差异保留的聊天组件副本；两份组件以同一共享格式化测试防止再次漂移。

已正确指定 `Asia/Shanghai` 的管理端内容审核展示、已经调用共享格式化函数的详情/日历/管理页面保持原实现，不因本次工作进行无关重构。

## 7. 生命周期与北京日期边界

### 7.1 客户端生命周期兼容

服务端 `has_started` 仍是分享页的权威值。确实需要本地回退且可能接收历史无时区值的详情、分享和管理兼容路径使用 `isBusinessDateTimeReached`。显式 ISO 的现有结果必须由特征测试证明保持不变。

不在可达业务路径中的普通绝对时间 `Date.parse`，例如签名 URL 到期和缓存 TTL，不属于本次修改范围。

### 7.2 内容审核日期筛选

管理端 `<input type="date">` 表达的是北京日历日期。API 把 `dateFrom` 和 `dateTo` 通过 `beijingDayUtcRange` 转为 UTC 边界后再查询：

- `dateFrom` 使用当天北京时间 00:00 对应的 UTC 起点。
- `dateTo` 使用下一天北京时间 00:00 对应的 UTC 排他终点。

仓储层绑定 `Date`/UTC 值，不再把日期文本当作 UTC 午夜。展示格式化本身已经正确，不修改。

### 7.3 同城发现排序

同城列表按用户看到的北京日历日分组，再按距离和开本时间排序。SQL 的日期排序键改为 UTC `start_at` 加固定八小时后的日期。该修改只改变查询结果顺序，不修改任何数据库记录。

`CURRENT_TIMESTAMP` 与正确 UTC `start_at` 的过滤比较继续保持原样。

## 8. 历史数据审计

本次只提供只读审计，不新增修复执行器，也不调用现有历史纠时接口：

- 审计命令只允许 `SELECT` 和本地报告输出。
- 报告包含车局 ID、当前值、北京时间展示、创建/更新时间、可用的纠时审计或通知证据、跨日影响和判定状态。
- 只有具备明确写入来源、纠时审计或外部原始时间证据的记录才能标为“有证据正确”或“有证据错误”。
- 仅凭 `DATETIME` 数字、创建日期或固定减八小时不能判定。
- 其余记录标记为“无法判定”，不生成可执行 SQL。

如果将来需要修改经人工确认的历史记录，必须另立操作任务，明确车局 ID、原值、证据、目标值、备份和回滚值，并再次取得用户授权。

## 9. 错误处理与兼容

- 前端无效 picker 值：阻止提交，不发请求。
- API 无效 `startAt`：返回稳定的 400 响应，事务内零业务写入。
- 展示无效值：沿用“时间待定”等现有 fallback，不猜测时间。
- 旧客户端无时区创建值：按北京时间兼容归一化；新客户端只发送显式 ISO。
- 正确显式 ISO：绝对时间语义和显示结果保持不变。
- 数据库连接、表结构和既有正确记录：完全不变。

## 10. 测试策略

### 10.1 正确行为保护测试

在修改实现前先增加特征测试：

- `2026-07-28T07:00:00.000Z` 始终显示北京时间 15:00。
- 显式 offset、`Date` 和现有改期/纠时行为保持不变。
- MySQL 连接仍为 UTC，迁移目录无变化。
- 分享页服务端生命周期值继续优先于客户端回退。

### 10.2 失败测试与修复闭环

每个确定错误先单独红灯，再做最小修复：

1. 北京 picker 15:00 发送 `07:00Z`。
2. API 把显式 ISO 和旧无时区值都绑定为正确 `Date`，非法值零写入。
3. UTC `DATETIME 07:00` 读回 ISO 后，各目标页面与通知显示 15:00。
4. ISO `07:00Z` 回填 picker 为 15:00。
5. 聊天短格式为 `07-28 15:00`。
6. 北京午夜附近的“今天/明天”不受设备时区影响。
7. 北京 23:30 与次日 00:30 使用正确日分组和排序。
8. 内容审核日期筛选使用北京时间日对应的 UTC 半开区间。
9. `talk` 在置顶缺失、`null` 或空白时均生成北京时间默认文案。

### 10.3 时区与集成矩阵

共享函数和关键客户端测试分别在以下进程时区运行，输出必须一致：

- `Asia/Shanghai`
- `UTC`
- `America/New_York`

增加真实 MySQL UTC 会话写入/读回测试，串联 picker、API 归一化、mysql2、JSON 和北京显示。无真实数据库时，单元测试不能替代该集成验收。

扩展 D47 时间契约检查，使创建、相册、资料审核、聊天、报名提示、订阅消息和 `talk` 纳入防回归范围。检查仅针对业务时间字段，不误报有效期、缓存或运维时间代码。

## 11. 发布顺序

1. 先发布向后兼容的 API 创建归一化，旧客户端随即停止产生新的错误时间。
2. 再发布小程序、管理端和固定后的 `talk` 子模块。
3. 不运行数据库迁移，不执行历史数据写入。
4. 生产环境只做健康检查、只读样本核对和错误率观察；创建写入闭环只在隔离测试环境验证。

## 12. 验收标准

- 完整闭环满足：选择 15:00 -> 请求 07:00Z -> DB 07:00 -> API 07:00Z -> 所有目标视图 15:00。
- 正确 ISO/UTC 样本改前改后结果一致。
- 创建入口不再向数据库绑定无时区原始字符串。
- 小程序、管理端、通知和聊天不再对目标业务字段使用设备本地 getter 或 ISO 字符串截取。
- 北京日筛选与跨午夜排序通过边界测试。
- 改期、历史纠时、UTC 数据库配置、绝对时间任务和正确展示路径测试全部保持通过。
- 数据库迁移目录无变化，生产库无自动数据写入。
- 全仓每个审计点均有“已修复并测试”或“已证明正确且不修改”的明确结论。
