# 剧本谜品牌重命名设计

## 目标

将平台品牌从“剧本迷·拼车”统一调整为“剧本谜”。拼车保留为平台内的一项具体功能，为后续增加其他功能留出品牌空间。

## 范围

### 小程序

- 首页启动标识从“拼”改为“谜”，启动标题改为“剧本谜”。
- 页面导航标题、分享标题、默认分享说明、登录提示统一使用“剧本谜”。
- `manifest.json` 与微信项目配置中的项目显示名改为“剧本谜”。
- 更新依赖旧品牌文案的首页冷启动与构建测试。

### Admin

- 浏览器标题改为“剧本谜管理后台”。
- 侧栏品牌改为“剧本谜管理”，登录页品牌改为“剧本谜管理后台”。
- 网页小程序工作区内的默认品牌分享说明改为“剧本谜，一起沉浸好本。”。

### CI 基线修复

- 恢复相册“打标签”操作缺失的 `tag-action` 样式类，使 `origin/develop` 现有 D53 静态契约重新通过。
- 只恢复契约要求的类名，不改变相册交互、数据或布局。

## 保留内容

以下内容不是品牌名，保持不变：

- “我的拼车日程”“拼车创建”“拼车编辑”“拼车说明”“拼车车局”等功能文案。
- 包名、目录名、环境变量、构建常量、字体文件名、API 域名、Docker 镜像名等 `pinche` 技术标识。
- 历史设计文档、历史评审材料和数据库种子中的历史或功能性文字。

## 实现方式

本次采用运行时品牌面精确替换，不进行全仓库机械替换。新增品牌契约测试，直接读取小程序和 Admin 的运行时源码与静态配置，验证：

- 运行时品牌文件不再包含“剧本迷”。
- 小程序启动标识为“谜”，品牌标题为“剧本谜”。
- 小程序和 Admin 的关键展示面都包含新品牌。
- 明确的拼车功能文案仍保留，防止误把功能名称一并删除。

品牌契约测试加入根项目的快速检查链，使本地检查和三条发布分支 CI 都能阻止旧品牌回归。

## 验证

按以下顺序验证：

1. 先运行新增品牌契约测试并确认在旧源码上失败。
2. 完成最小品牌替换与 D53 基线修复后，确认品牌契约测试和 D53 检查通过。
3. 构建小程序与 Admin。
4. 运行完整 `npm run check`。
5. 检查 Git 差异，确保只包含设计、测试、品牌文案和获准的基线修复。

## 发布与小程序上传

验证通过后，将同一组提交依次发布：

1. 推送到 `develop`，等待 GitHub Actions 成功。
2. 将已验证的 `develop` 合并到 `main`，推送并等待 CI 成功。
3. 将已验证的 `main` 合并到 `publish`，推送并等待 CI 成功。
4. 使用生产配置重新构建小程序，通过微信开发者工具 CLI 上传代码，形成微信公众平台开发版本。

本次不自动提交微信审核，也不自动发布线上小程序版本。

## 失败处理

- 任一分支 CI 失败时停止后续分支晋级，记录运行编号并修复后重新验证。
- 微信开发者工具 CLI、登录态或上传权限不可用时，保留已完成的三分支发布结果并报告具体阻塞，不伪造上传成功。
- 当前主工作区中的未提交文件不进入本次提交。
