# 角色认领必备资料需求

## 目标

把玩家角色和 NPC 角色认领统一为“先完成可识别资料，再按车头设置直接上车或提交审核”。车头只决定是否需要审核，不再决定是否需要手机号。系统必须在后端强制要求昵称和已验证手机号；新用户还必须至少成功提交过一次头像，头像异步审核不得阻塞认领，未通过前统一展示默认头像。

## 术语

- **角色认领**：用户在车局分享页选择玩家座位或 NPC 角色，并直接上车或提交车头审核。
- **直接认领**：车局 `join_policy = direct`，满足资料要求后立即绑定角色。
- **审核认领**：车局 `join_policy = review_required`，满足资料要求后创建待审核申请。
- **历史用户**：本功能数据库迁移执行前已存在的用户。
- **新用户**：本功能数据库迁移执行后创建的用户。
- **完成头像选择**：用户选择的头像已经成功上传、建立头像资产记录并进入内容审核；不要求审核通过。
- **可展示头像**：关联头像资产处于 `active`，且审核状态为 `approved` 或 `approved_legacy`。

## 功能需求

1. 车头创建和管理车局时，只能配置是否需要上车审核；不得再展示或保存“上车必须留电话”开关。
2. 玩家座位直接认领、玩家座位审核申请、NPC 角色直接认领和 NPC 角色审核申请必须使用同一套资料准入规则。
3. 资料准入必须由后端强制执行，不能只依赖小程序前端校验。
4. 用户提交任何角色认领动作前必须已经登录。
5. 用户提交任何角色认领动作前必须具有已经安全审核并持久化的非空昵称；不得用待审昵称或 `openid` 代替昵称满足准入。
6. 用户提交任何角色认领动作前必须具有微信授权并由后端记录为已验证的手机号。
7. 新用户提交任何角色认领动作前，必须至少完成一次头像选择。
8. 历史用户无论是否上传过头像，都视为已经满足头像选择要求；历史用户仍必须具有昵称和已验证手机号。
9. 头像成功入库并进入异步审核后，应立即满足头像选择要求；不得等待审核通过才允许直接认领或提交申请。
10. 头像处于 `pending`、`review`、`error`、`rejected`，或没有可展示头像时，车头和其他用户只能看到系统默认头像。
11. 头像资产建立时应关联为用户当前头像候选；头像变为 `approved` 或 `approved_legacy` 后，后续读取应自动展示真实头像，不要求用户再次保存头像、重新提交认领或申请。
12. 头像后来被拒绝、隐藏或清理，不得撤销、驳回或改变已经提交或已经通过的认领；展示退回系统默认头像。
13. 直接认领模式下，资料满足后应延续现有直接绑定玩家座位或 NPC 角色的行为。
14. 审核认领模式下，资料满足后应延续现有创建待审核申请的行为。
15. 小程序点击玩家座位或 NPC 角色时，应按“登录、补齐昵称与首次头像选择、授权手机号、继续原认领动作”的顺序引导；已经满足的步骤应跳过。
16. 新用户在必填资料弹窗中必须填写昵称并选择头像；头像进入异步审核时，前端应保存昵称并继续手机号授权，不得把 `202 CONTENT_MODERATION_REVIEW_PENDING` 当作流程失败。
17. 历史用户缺少头像时，资料弹窗不得强制其重新选择头像。
18. 后端必须为缺昵称、缺已验证手机号、缺首次头像选择返回可区分的稳定错误码，供前端恢复到对应补全步骤。
19. 角色卡、车头审核列表和成员相关展示不得回退显示完整 `openid`；昵称异常缺失时统一显示“车友”。
20. `join_phone_required` 数据库字段可以为兼容历史数据保留，但创建、更新、详情和认领准入不得再让该字段改变“手机号必填”的结果。
21. 玩家和 NPC 的车头安排、管理员操作、踢人、换选、取消申请以及非认领业务不得被本功能扩大或改变。

## 数据与迁移需求

1. `users` 必须新增可持久判断“完成头像选择”的时间字段；不得用当前 `avatar_url` 是否为空推断，因为待审或驳回头像不应失去完成状态。
2. 迁移必须先为所有历史用户回填该时间字段，再让迁移后的新用户默认保持未完成。
3. 头像资产成功建立时必须幂等地写入完成时间并关联当前头像候选；同一上传重试不得清空或重复改变既有完成状态。
4. 当前用户接口和本地登录态必须返回该状态，使前端能够跳过历史豁免或已完成头像选择的步骤。
5. 迁移协调必须只在首次增加字段时回填当时已有用户；后续重复启动不得把迁移后新用户的空值误判为历史漏迁或自动豁免。

## 安全与隐私需求

1. `openid` 继续作为内部微信身份标识，但不得作为普通用户可见名称。
2. 完整手机号不得新增到公开车局、分享页、角色卡或其他玩家可见响应中。
3. 本功能不改变手机号加密存储方式。
4. 待审、复审、错误或驳回头像不得通过角色详情、分享页、车头审核列表或媒体静态路径泄露。
5. 前端旧版本或手工 API 请求缺少必备资料时，后端必须拒绝认领。

## 非目标

- 不新增实名认证、身份证、真实姓名或通讯录验证。
- 不要求头像审核通过后才能认领。
- 不让车头手工审核头像内容。
- 不向车头展示完整手机号，也不新增手机号搜索。
- 不移除数据库中的 `join_phone_required` 历史字段。
- 不改变车头是否审核的 `join_policy` 语义。
- 不改变 NPC 是否允许自选的 `npc_join_enabled` 设置。
- 不重做个人中心或车局分享页整体视觉。
- 不追溯撤销历史认领。

## 验收标准

1. 创建车局页和管理车局页只显示“上车审核”，不再显示“上车必须留电话”。
2. 新建和更新车局的前端请求不再发送可关闭手机号要求的值。
3. 后端对所有玩家/NPC直接认领和审核申请固定要求已验证手机号。
4. 缺昵称时四条认领路径均被后端以稳定错误码拒绝。
5. 新用户未完成头像选择时四条认领路径均被后端以稳定错误码拒绝。
6. 历史用户缺头像但有昵称和已验证手机号时可以直接认领或提交审核。
7. 新用户头像上传返回待审后，无需等待审核结果即可继续直接认领或提交审核。
8. 待审、复审、错误和驳回头像在角色卡与审核列表中显示默认头像；审核通过后自动显示真实头像。
9. 昵称缺失的异常历史记录显示“车友”，不显示 `openid`。
10. 旧客户端把 `joinPhoneRequired: false` 发给创建或更新接口时，手机号仍然是认领必填项。
11. API 自动化测试、静态检查和小程序构建全部通过。
12. 微信开发者工具中手动验证直接认领与审核认领各一条完整流程。
